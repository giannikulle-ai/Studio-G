The fallback. Six lines of shell on each Pi. "Down" is a state you can read from bed, never a blank screen.
# scripts/kiosk.sh — loops on each Pi
URL=https://pw1x.tail.ts.net/screens/bench   # or /screens/night
DOWN=https://pw1x-down.pages.dev
if curl -fsS -m 5 https://pw1x.tail.ts.net/healthz >/dev/null; then want=$URL; else want=$DOWN; fi
[ "$want" != "$(cat /run/kiosk.current)" ] && { echo "$want" > /run/kiosk.current; chromium --kiosk "$want" & }
sleep 30

One process

Node · TypeScript · SSE · SQLite

One service on PW-1x. The browser gets one page and one event stream. Everything the page shows comes from adapters; everything it does is a verb on one. The service itself has no idea what Claude is.

Stack

kept boring on purpose
LayerChoiceWhy this and not more
runtimeNode 22 · TypeScript · one systemd unit in the container sliceThe Remote API and the MCP SDK are both easiest from TS; studio-local is TS already, so one toolchain.
httpFastify, or Node's http if it stays under ten routes · one static index.htmlSmall enough to rewrite in a weekend. No SPA framework: a few hundred lines of DOM code driven by one JSON list of adapters.
streamsServer-Sent Events · one GET /api/events per browser · Last-Event-ID replay from a ring bufferOne direction is enough; every action is a POST. Reconnects are free in the browser; no WebSocket library, no fan-out server.
storeSQLite via better-sqlite3 · console.sqlite for runs and chains · read-only attach of studio-local's work_log.sqliteTwo writers, two files, one ATTACH for the joined view. WAL mode so readers never block the door.
validationJSON Schema (Ajv) · one schema per verb, shipped to the browser as-isThe same schema renders the form and validates the POST. A verb is a schema plus a function; nothing else to keep in sync.
secretssops + age · decrypted to /run/studio/secrets.env at boot · adapters read process.envKeys live in the repo encrypted; adapter source never contains one.
front doorCaddy · pw1x.tail.ts.net · reverse_proxy localhost:8787Tailscale identity is the login. No user table, no session cookie, no password page.
metrics/metrics from the console itself: verb runs, SSE clients, adapter status agePrometheus already scrapes the box; the console is one more target, so its own health lands on the bench screen.

Shape

the adapter, the event, the run

Three types carry the whole thing. The first is from adapters/README.md; the other two are what the service adds around it.

adapters/_template.ts

export interface Adapter {
  id: string;                        // "usb-light"
  kind: "session" | "call" | "device" | "service" | "outbound";
  status(): Promise<Status>;         // cached; polled on an interval the adapter sets
  events(): AsyncIterable<Event>;    // long-lived; the hub re-subscribes on throw
  verbs: Verb[];
}
export interface Verb {
  name: string;
  schema: JSONSchema;                 // renders the form, validates the POST
  stream?: boolean;                   // true: result arrives as events under run_id
  run(input: unknown, ctx: Ctx): Promise<Result>;
}
export interface Status {
  state: "ok" | "warn" | "stop" | "idle";
  summary: string;                    // the pill
  fields: Record<string, string>;   // the small facts
  items?: Item[];                     // sessions, jobs: rows with their own verbs
}

-- console.sqlite
CREATE TABLE runs (
  run_id     TEXT PRIMARY KEY,
  ts         TEXT NOT NULL,
  adapter    TEXT NOT NULL,   verb TEXT NOT NULL,
  input      TEXT NOT NULL,   -- JSON, after fromResultOf() was resolved
  parent_run TEXT,            -- the run whose result fed this one: the chain
  status     TEXT NOT NULL,   -- queued | running | done | failed
  result     TEXT,            -- JSON; files as path refs
  ms         INTEGER
);
CREATE VIEW work_log AS            -- what the panel shows
  SELECT ts, 'console' src, adapter||'.'||verb what, NULL backend, NULL tok_in, NULL tok_out, ms FROM runs
  UNION ALL
  SELECT ts, source, tool, backend, tokens_in, tokens_out, latency_ms FROM local.calls;

A handoff, step by step

from your seat

The chain in the work log, as the service sees it. Nothing here is a bus; it is one verb whose input names another verb's result, run by you.

  1. You ask local. The browser POSTs to /api/local-models/ask; the verb runner validates against the schema and writes a runs row, run_9f3.POST /api/local-models/ask { model:"auto", text:"…", turns:6 }
  2. The adapter calls the door. One request to studio-local's /v1/chat/completions with source: console, streaming. Chunks come back as chunk events under run_9f3; the page appends them. The door logs the call in its own table.the door picks the backend: desktop if idle, else PW-1x · logged · metered · light on
  3. The result is stored as a path under /srv/studio/results/run_9f3/brief.md. "Hand result to…" now offers every adapter with a verb that takes files.GET /api/results/run_9f3 → { files:["…/brief.md"] }
  4. You create a session and pick "files: from local #9f3". The form fills files: fromResultOf("run_9f3"); the runner resolves it to paths, sets parent_run, and the adapter calls the Remote API's create.POST /api/claude-code-remote/create { prompt:"…", files: fromResultOf("run_9f3") } → session_digest
  5. The session streams back through the adapter's events(), which polls the Remote API for every live session and tags each line with its session id. If the session calls studio-local over MCP mid-task, that lands in the same log as source = claude. A bonus, not the mechanism.
  6. Overnight, the same shape without you. A routine arms; batch_job returns at once; when it finishes, studio-local POSTs to /hook/local-models, the adapter emits done, and the routine's watch fires send to wake the session. parent_run still links the chain.POST /hook/local-models { job_id:"job_7c2", status:"done" } · secret checked · → send(session_falsework, "job_7c2 is done")

Why the page can stay dumb. It never special-cases an adapter. It renders status.fields as small facts, status.items as rows with their own buttons, events as a tail, and each verb.schema as a form. A property named files gets the "from another adapter's result" picker; a property with enum gets a select; a stream: true verb renders its chunks inline. That is the entire rendering vocabulary, and it is why the Claude section and the printer tile are the same code.

Decisions in the mockup

reversible, but named
ChoiceWhyThe alternative
one SSE streamOne connection per browser; the page filters by adapter. Reconnect replays from one ring buffer.A stream per adapter. Simpler server, eight connections per tab, eight reconnects.
forms from schemaA verb is a schema and a function. The form, the validation and the docs are one artefact.Hand-written forms per verb. Nicer for two verbs, a drift bill by the twentieth.
results as pathsFiles stay on PW-1x under /srv/studio/results/; a handoff passes paths, so a 40-file brief costs nothing to hand on.Inline results in SQLite. Fine for text, wrong for files.
Tailscale is the loginNo user table, no password page. The phone and the screens are on the tailnet already.Cloudflare Access in front of everything. Needed only for the second-location screen, so it stays a per-route choice.
white, black, one redNothing but type, space and rules. Square corners, no shadows, no tints; red is spent only on the light, the live things and Stop, so it means something. The severity is the point: it never distracts from the numbers.Warmth and rounded surfaces. Friendlier; easier to make ordinary.
the console has its own /metricsIts health lands on the bench screen next to the model's, so "the console is down" is visible where you'd look.Trust /healthz alone. Enough for the kiosks, blind for you.
