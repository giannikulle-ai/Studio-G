How it's built

Everything above is the console at 1240 px · example data as at A5 · nothing calls a real backend

What earns a place on it

The kiosk screens already do the glancing. So the console is where you act, and the test for anything on it is whether you would touch it. Four things from the earlier drafts are gone.

On the page

  • Is it up, and is work happening. The header: one dot, the work-and-serve split, and the light. The split is PW-1x's double life in one control, and it opens the dashboard.
  • What needs you. Lost in the jungle. A session that stopped, a result nobody read, an alert still firing. When it empties it says so.
  • What's moving. Navigating. The sessions running right now, and the jobs they are waiting on. Every row carries the same identifying line as the log: when it started, who started it, its id, and how long it has run.
  • The tools. Eight brackets: the bots, the projects, the models, the dashboards, the disks, the connections, the printer, and room for more.
  • The log. History only, newest first, every call tagged with who made it. Anything still running is above it in Navigating, so nothing appears twice. The day's totals sit under the heading.

Not on the page

  • CPU, memory, temperatures, tokens per second. Screen A and Grafana own these. The console needs "up" and a way through to the graphs.
  • The printer, until it needs you. It is not a session, so it is not in Navigating. Its buttons are in the Printer tools, and a failed print shows up in the jungle like anything else that stops.
  • Which backend holds which model. The door picks. It appears under Local models because you occasionally swap them, not because you watch them.
  • A row of big numbers. Two of the four on the last draft were statistics invented to fill the row.

Most days nothing is wrong, so the resting state of this page is a short list and a quiet log. That is the design, not an empty state.

One process

One Node service on PW-1x. The browser gets one page and one event stream. Everything shown comes from an adapter; everything you do is a verb on one. The service knows nothing about Claude specifically.

What the sketch decided

From the sketchHow it is built
Where are we?The first thing on the page, left column. Lost in the jungle is anything stopped, failed, alerting, or finished and unread, whatever kind of thing it is. Navigating is the active sessions and the jobs they are waiting on. An empty jungle prints On course.
The chevronOpens the row in place rather than navigating away: the last three events from that thing's stream, then its actions as buttons. Verb is the word adapters/README.md already uses for an action an adapter can perform, so the buttons under a row are that adapter's verbs. One control shows status(), events() and verbs[] at once, which is why every row is the same component.
Log, swapped rightHistory, under a reserved block and the day's totals. Every line comes from the joined view over the console's runs table and the door's calls table, so who did it is a filter rather than a guess. It scrolls inside a fixed height so the column ends where the tools do.
Percent split, work and serverPW-1x is two machines in one box, so the header reads 61% work · 12% serving under the label PW-1x load, and opens Grafana. It is a labelled readout rather than a gauge: the numbers only mean anything next to the words, which the first attempt left out.
Tool sectionSeven bracketed tiles of buttons, and one empty dashed box. A tile groups adapters rather than being one: Bot Land is every session connector, Connections every piece of plumbing. Nothing in a tile carries a status, because a button should say what it does and nothing else. The dashed box is the hook the README promises, and a bare outline is how this page says a thing is unfinished.
Studio settingsThe one icon button. Secrets, adapters, screens and the sops file, none of which belong on a page you look at all day.

One addition to the sketch: the light. It gets its own control because "is anything running" and "is the light on" are the same fact, and the light is the ambient version of this whole page. Auto follows the Prometheus alert; the button holds it on or off.

The shape underneath

Three types carry all of it. The first is from adapters/README.md; the other two are what the service adds around it.

adapters/_template.ts

export interface Adapter {
  id: string;                        // "usb-light"
  kind: "session" | "call" | "device" | "service" | "outbound";
  status(): Promise<Status>;         // cached, polled on the adapter's own interval
  events(): AsyncIterable<Event>;    // long-lived; the hub resubscribes on throw
  verbs: Verb[];
}
export interface Verb {
  name: string;
  schema: JSONSchema;                // draws the form, validates the POST
  stream?: boolean;                  // true: the answer arrives as events under run_id
  run(input: unknown, ctx: Ctx): Promise<Result>;
}
export interface Status {
  state: "lost" | "waiting" | "moving" | "idle";   // which group the row appears in
  line: string;                      // the row's sentence
  sub?: string;                      // the grey line under it
  items?: Item[];                    // sessions and jobs: rows with their own verbs
}

state is the only thing the page needs in order to sort an adapter into Lost in the jungle or Navigating. Nothing else in the UI knows what a session or a printer is.

-- console.sqlite
CREATE TABLE runs (
  run_id     TEXT PRIMARY KEY,
  ts         TEXT NOT NULL,
  adapter    TEXT NOT NULL,   verb TEXT NOT NULL,
  input      TEXT NOT NULL,   -- JSON, after fromResultOf() resolved
  parent_run TEXT,            -- the run whose result fed this one: the chain
  status     TEXT NOT NULL,   -- queued | running | done | failed
  result     TEXT,            -- JSON; files as path references
  ms         INTEGER
);
CREATE VIEW work_log AS          -- what the log panel reads
  SELECT ts, 'you' src, adapter||'.'||verb what, NULL backend, ms FROM runs
  UNION ALL
  SELECT ts, source, tool, backend, latency_ms FROM local.calls;

A handoff, step by step

The one thing this console does that nothing else does: a verb whose input is another verb's result, run by you, recorded as a chain.

  1. You ask local. The browser posts to the runner, which validates against the schema and writes a runs row.POST /api/local-models/ask { model:"auto", text:"…", turns:6 } → run_9f3
  2. The adapter calls the door. One streaming request to studio-local's /v1 with source: console. Chunks come back as events under the run id, the page appends them, the door logs the call, and the light comes on.the door picks the backend: the desktop when idle, else PW-1x
  3. The result is stored as a path, not as text in a row. "Hand it on" now offers every adapter with a verb that takes files./srv/studio/results/run_9f3/brief.md
  4. You hand it to a session. The form fills files: fromResultOf("run_9f3"); the runner resolves it to paths, sets parent_run, and the adapter calls create.POST /api/claude-code-remote/create → session_digest
  5. The session streams back through the adapter's events(). If it calls the door itself over MCP mid-task, that is recorded in the same log under source = claude. A bonus, not the mechanism.
  6. Overnight, the same shape without you. A routine arms, batch_job returns at once, and when it finishes the door posts to /hook/local-models; the adapter emits done and the routine's watch wakes the session. parent_run still links the chain.POST /hook/local-models { job_id:"job_7c2", status:"done" }

Named, and reversible

ChoiceWhyThe alternative
Colour only means stateThree colours on the whole page: lost, waiting, moving. Nothing else is tinted, so anything coloured is something to look at. Everything else is ink, paper and rules.A brand accent, which competes with the one signal the page exists to carry.
Questions in serif"Where are we?", "Lost in the jungle" and "On course" are your words, so they are set in a serif. The machine answers in sans and mono. The two voices never blur.One typeface throughout. Tidier, and it loses the joke.
The chevron opens in placeDetail is three events and the verbs for that thing. No second page, no modal, no lost context.A detail route per adapter. More screens to design, and you lose the list while you read one row.
One page, no tabsThe sketch has no tabs. The console is one screen; graphs are Grafana's job and settings sit behind the one icon.Tabs for bench, log and tools, which hide the thing you came for behind a click.
Results are pathsFiles stay on PW-1x under /srv/studio/results/, so handing a forty-file brief to a session costs nothing.Results inline in SQLite. Fine for text, wrong for files.
Tailscale is the loginNo user table, no password page. The phone and the screens are on the tailnet already.Cloudflare Access in front of everything, which only the second-location screen actually needs.
