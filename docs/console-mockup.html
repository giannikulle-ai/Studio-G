The fallback. Six lines of shell on each Pi: curl the console's /healthz; on failure load the static page; on success load the kiosk URL. The nightstand screen is never blank, and "down" is a state you can read from bed.
# scripts/kiosk.sh — runs in a loop on each Pi
URL=https://pw1x.tail.ts.net/screens/bench   # or /screens/night
DOWN=https://pw1x-down.pages.dev
if curl -fsS -m 5 https://pw1x.tail.ts.net/healthz >/dev/null; then want=$URL; else want=$DOWN; fi
[ "$want" != "$(cat /run/kiosk.current)" ] && { xdotool key F5; echo "$want" > /run/kiosk.current; chromium --kiosk "$want" & }
sleep 30

Figure 1 · One process

A viewer with buttons over adapters

One Node/TypeScript service on PW-1x. The browser gets one HTML page and one SSE stream. Everything the page shows comes from adapters; everything it does is a verb on one. The service itself has no idea what Claude is.

Stack

Kept boring on purpose

LayerChoiceWhy this and not more
runtimeNode 22 · TypeScript · one systemd unit, console.service, in the container sliceThe Claude Code Remote API and the MCP SDK are both easiest from TS; studio-local is TS already, so one toolchain.
httpFastify (or Node's http if it stays under ten routes) · one static index.htmlSmall enough to rewrite in a weekend. No SPA framework: the page is a few hundred lines of DOM code driven by one JSON list of adapters.
streamsServer-Sent Events · one GET /api/events per browser · Last-Event-ID replay from a ring bufferOne direction is enough; every action is a POST. Reconnects are free in the browser; no WebSocket library, no fan-out server.
storeSQLite via better-sqlite3 · console.sqlite for runs and chains · read-only attach of studio-local's work_log.sqliteTwo writers, two files, one ATTACH for the joined view. WAL mode so readers never block the door.
validationJSON Schema (Ajv) · one schema per verb, shipped to the browser as-isThe same schema renders the form and validates the POST. A verb is a schema plus a function; nothing else to keep in sync.
secretssops + age · decrypted to /run/studio/secrets.env at boot · adapters read process.envKeys live in the repo encrypted; adapter source never contains one.
front doorCaddy · pw1x.tail.ts.net · reverse_proxy localhost:8787Tailscale identity is the login. No user table, no session cookie, no password page.
metrics/metrics from the console itself: verb runs, SSE clients, adapter status agePrometheus already scrapes the box; the console is one more target, so its own health lands on Screen A.

Shape

The adapter, the event, the run

Three types carry the whole thing. The first is from adapters/README.md; the other two are what the service adds around it.

adapters/_template.ts

export interface Adapter {
  id: string;                        // "usb-light"
  kind: "session" | "call" | "device" | "service" | "outbound";
  status(): Promise<Status>;         // cached; polled on an interval the adapter sets
  events(): AsyncIterable<Event>;    // long-lived; the hub re-subscribes on throw
  verbs: Verb[];
}
export interface Verb {
  name: string;
  schema: JSONSchema;                 // renders the form, validates the POST
  stream?: boolean;                   // true: result arrives as events under run_id
  run(input: unknown, ctx: Ctx): Promise<Result>;
}
export interface Status {
  state: "ok" | "warn" | "stop" | "idle";
  summary: string;                    // the chip
  fields: Record<string, string>;   // the k/v grid on the card
  items?: Item[];                     // sessions, jobs: rows with their own verbs
}

-- console.sqlite
CREATE TABLE runs (
  run_id     TEXT PRIMARY KEY,
  ts         TEXT NOT NULL,
  adapter    TEXT NOT NULL,   verb TEXT NOT NULL,
  input      TEXT NOT NULL,   -- JSON, after fromResultOf() was resolved
  parent_run TEXT,            -- the run whose result fed this one: the chain
  status     TEXT NOT NULL,   -- queued | running | done | failed
  result     TEXT,            -- JSON; files as path refs
  ms         INTEGER
);
CREATE VIEW work_log AS            -- what the panel shows
  SELECT ts, 'console' src, adapter||'.'||verb what, NULL backend, NULL tok_in, NULL tok_out, ms FROM runs
  UNION ALL
  SELECT ts, source, tool, backend, tokens_in, tokens_out, latency_ms FROM local.calls;

Sequence

A handoff, from your seat

The chain in the work log panel, step by step. Nothing here is a bus; it is one verb whose input names another verb's result, run by you.

  1. You click ask on the local-models card and type the question. The browser POSTs to /api/local-models/ask; the verb runner validates against the schema and writes runs row run_9f3. POST /api/local-models/ask { model:"auto", text:"…", turns:6 }
  2. The adapter calls the door. One request to studio-local's /v1/chat/completions with source: console, streaming. Chunks come back as chunk events under run_9f3; the card appends them. The door logs the call to its own calls table. studio-local picks the backend: desktop if idle, else PW-1x · logged · metered · light on
  3. The result is stored as runs.result, a path under /srv/studio/results/run_9f3/brief.md. The card's "hand result to…" button now offers every adapter with a verb that takes files. GET /api/results/run_9f3 → { files:["…/brief.md"] }
  4. You click create on claude-code-remote and pick "files: from local-models #9f3". The form fills files: fromResultOf("run_9f3"). The verb runner resolves it to the path list, sets parent_run = run_9f3, and the adapter calls the Remote API's create with the prompt and files. POST /api/claude-code-remote/create { prompt:"…", files: fromResultOf("run_9f3") } → session_digest
  5. The session streams back through the adapter's events(), which polls the Remote API's events for every live session and tags each line with its session id. It shows on the card and in the log. If the session itself calls studio-local over MCP mid-task, that lands in the same work_log view as source = claude; a bonus, not the mechanism.
  6. Overnight, the same shape without you. A schedule verb arms a routine; batch_job returns at once; when it finishes, studio-local POSTs to /hook/local-models, the adapter emits a done event, and the routine's watch fires claude-code-remote.send to wake the session. parent_run still links the chain. POST /hook/local-models { job_id:"job_7c2", status:"done" } · secret checked · → send(session_falsework, "job_7c2 is done")

Why the UI can stay dumb. The page never special-cases an adapter. It renders status.fields as a grid, status.items as rows with their own verb buttons, events as a tail, and each verb.schema as a form. A schema property named files gets the "from another adapter's result" picker; a property with enum gets a select; a stream: true verb renders its chunks inline. That is the entire rendering vocabulary, and it is why the Claude card and the printer card are the same component.

Build order

  1. Skeleton on the desktop. Server, SSE hub, runner, one fake adapter with a tick verb. Page renders one card from the shape. Nothing from PW-1x.
  2. claude-code-remote. Sessions list, create and send, events polling. Testable today against the Remote API with your key in the sops file.
  3. local-models against Ollama. The ask verb streams; the work log view joins studio-local's table. This is the A0 baseline with an interface on it.
  4. First handoff. fromResultOf() end to end: ask → create. The chain shows in the panel.
  5. A5, on PW-1x. pw1x from Prometheus, usb-light from Alertmanager, the screen routes, kiosk.sh. Then p2s, github, cloudflare, phone as their afternoons come.

Decisions in the mockup

Reversible, but named

ChoiceWhyThe alternative
one SSE stream, not one per cardOne connection per browser; the page filters by adapter. Reconnect replays from one ring buffer.A stream per adapter. Simpler server, eight connections per tab, eight reconnects.
schema-rendered formsA verb is a schema and a function. The form, the validation and the docs are one artefact.Hand-written forms per verb. Nicer for two verbs, a drift bill by the twentieth.
results as path referencesFiles stay on PW-1x under /srv/studio/results/; a handoff passes paths, so a 40-file brief costs nothing to hand on.Inline results in SQLite. Fine for text, wrong for files.
Tailscale identity is the loginNo user table, no password page. The phone and the screens are on the tailnet already.Cloudflare Access in front of everything. Needed only for the second-location screen off the tailnet, so it stays a per-route choice.
dark-first, amberIt is a control room; the screens are on all night. The Systems Map's tokens, roles swapped, so the docs and the tool read as one family.Light-first like the documents. Correct for reading, wrong at 02:00.
the console has its own /metricsIts health lands on Screen A next to the model's, so "the console is down" is visible where you'd look.Trust /healthz alone. Enough for the kiosks, blind for you.

None of this edits the Systems Map or the READMEs. It draws what they already say and names the few choices they left to the first code. When a choice here is confirmed it belongs in console/README.md, not here.
