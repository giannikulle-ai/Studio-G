How It's Built

One Node service on PW-1x. The browser gets one page and one event stream. Everything shown comes from an adapter; everything you do is a verb on one, which is the word adapters/README.md uses for an action an adapter performs. The service knows nothing about Claude specifically.

What Earns a Place on the Page

The kiosk screens do the glancing, so the console is where you act. The test for anything on it is whether you would touch it.

On the page

  • Where Are We. Lost in the Jungle is anything stopped, failed, alerting, or finished and unread. Navigating is the active sessions and the jobs they wait on. Each row carries the same identifying line as a log entry.
  • Token Spend. Frontier tokens are the ones you pay for, so that number leads. The bar is how much of today's work local absorbed instead.
  • Tools. Seven rectangles and one empty dashed one for whatever comes next.
  • The Log. History only, newest first, tagged with who made each call. The three statistics above it are yours to pick.

Not on the page

  • Processor, memory, temperature, tokens per second. Screen A and Grafana own these. The header carries the load split and opens the dashboard.
  • Up or down. The console is served from PW-1x, so if the box is down this page is not here to tell you.
  • The light. It follows the alert rule by itself. The manual override is in these settings, where you will almost never need it.
  • The printer, until it needs you. It is not a session, so it is not in Navigating. A failed print shows up in the jungle like anything else that stops.

The Shape Underneath

adapters/_template.ts

export interface Adapter {
  id: string;                        // "usb-light"
  kind: "session" | "call" | "device" | "service" | "outbound";
  status(): Promise<Status>;         // cached, polled on its own interval
  events(): AsyncIterable<Event>;    // long-lived; the hub resubscribes on throw
  verbs: Verb[];                     // the buttons a row shows when you open it
}
export interface Status {
  state: "lost" | "waiting" | "moving" | "idle";  // which group the row appears in
  line: string;                      // the row's sentence
  sub?: string;                      // the grey line under it
  items?: Item[];                    // sessions and jobs: rows with their own verbs
}

the run in the table

-- console.sqlite
CREATE TABLE runs (
  run_id     TEXT PRIMARY KEY,
  ts         TEXT NOT NULL,
  adapter    TEXT NOT NULL,   verb TEXT NOT NULL,
  input      TEXT NOT NULL,   -- JSON, after fromResultOf() resolved
  parent_run TEXT,            -- the run whose result fed this one: the chain
  status     TEXT NOT NULL,   -- queued | running | done | failed
  result     TEXT,            -- JSON; files as path references
  ms         INTEGER
);
CREATE VIEW work_log AS          -- what the log panel reads
  SELECT ts, 'you' src, adapter||'.'||verb what, NULL backend, ms FROM runs
  UNION ALL
  SELECT ts, source, tool, backend, latency_ms FROM local.calls;

A Handoff, Step by Step

  1. You ask local. The browser posts to the runner, which validates against the schema and writes a runs row.POST /api/local-models/ask → run_9f3
  2. The adapter calls the door. One streaming request to studio-local's /v1 with source: console. The door logs the call and the light comes on by itself.
  3. The result is stored as a path, not as text in a row./srv/studio/results/run_9f3/brief.md
  4. You hand it to a session. The form fills files: fromResultOf("run_9f3"); the runner resolves it to paths and sets parent_run.
  5. Overnight, the same shape without you. A routine arms, batch_job returns at once, and the door posts to /hook/local-models when it finishes, which wakes the session.
