Studio-G Systems Map

Everything on the bench, everything on the wire, and the one place it all reports to. PW-1x is the engine; this is the vehicle around it. Solid lines are bought or decided. Dashed lines are hooks left open on purpose.

Figure 1 · Physical layer

What is on the bench, and what it plugs into

One inference box, one desktop, three screens in three places, one light, and four sockets left open. Everything reaches PW-1x over the LAN except the second-location screen, which comes in over the internet.

Figure 2 · The one place

Claude manages local; the console watches

You work in Claude Code. PW-1x's local models are tools it calls. The control room beside it shows what's running and hands you verbs — and never sits between you and Claude.

"Have them talk to each other" — what that is now

A tool call. Claude asks studio-local to read a repo and brief it; the brief lands in Claude's context and Claude carries on. No model needs to know another exists. For overnight work, batch_job returns at once and PW-1x wakes the session by webhook when it's done. Handing one Claude session's result to another is a console verb — create a session with that result as its input — and the work log records the chain. That's the whole mechanism. There's no bus, because Claude Code already speaks MCP and git.

Figure 3 · Where things live, who watches

Projects on the left, telemetry on the right

Two independent circuits. Projects have one source and two deploy targets, and anything public leaves through Cloudflare rather than an open port. Every screen and the light read the same telemetry.

Before building

Where the five questions landed

  1. Which 4060? — The 4060 Ti stays in the PC. PW-1x starts CPU-only and the PC becomes a best-effort fast tier over 10GbE. Not cooked: decode is RAM-bound either way, so the 120b still runs — what you lose is prefill, which on Zen 2 without a GPU is minutes on a big repo context. Overnight batch is fine; interactive is not. Now open: the GPU path for PW-1x — run CPU-only and measure first (free), a 16GB card (~$430–450) to restore the design as drawn, or the used 3090 (~$1,000) that was already rank 1 on the Handoff's list. And whether the PC's tier is best-effort or a reserved VRAM slice.
  2. Subscription or API? — Subscription, through Claude Code. Claude manages; local models are tools it calls over MCP. Nothing needs API keys unless it must run with no Claude session at all, and nothing does at launch. Consequence: one bill, one code path. The first draft had a local Foreman dispatching to Claude as a tier — that was backwards, and it's gone.
  3. Screen A — small board + panel. Pi Zero 2 W class, 7" 1024×600 HDMI panel, USB power from PW-1x, a cable to PW-1x's second 10GbE port so it stays up when the router doesn't. Consequence: the 4060 Ti question above is unaffected — no display stack on the inference box either way.
  4. Which Bambu? — P2S. My mistake: "PS2" was a transposition, not a wrong model. 256×256×256 enclosed CoreXY, 5" touchscreen, 1080p30 camera with AI failure detection, dual-band Wi-Fi, $799 as the Combo with AMS 2 Pro. LAN mode plus Developer Mode opens MQTT, FTP and the camera stream; the ha-bambulab integration already supports it. Consequence: nothing in the hook changes. The camera stream is a bonus panel for Screen A, and AI-detection events become alerts on B and C.
  5. Console — on PW-1x, with a static fallback. Behind Caddy, next to the models. A "PW-1x is down" page on Cloudflare Pages that every kiosk swaps to when a 30-second health check fails. Consequence: six lines of shell on each Pi. The nightstand screen is never blank.

Still open: the PW-1x GPU path · whether the PC tier is best-effort or reserved · which iPad generations are on the Apple list (it decides whether the driver boards are commodity or a hunt).
