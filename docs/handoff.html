Layer 1 · Non-technical

What this is and where it stands

For anyone tracking scope, budget and timeline who will not touch the hardware.

The problem

Agent-based coding and automation work is consuming a full monthly allotment on a commercial AI plan, and hitting per-session rate limits multiple times in a single day under normal use. That is a capacity ceiling, not a cost overrun — additional spend does not buy past a rate limit.

A locally owned server has no rate limit. It is slower than the commercial service, so it does not replace it. It absorbs the high-volume, low-difficulty share of the work — file reads, summarisation, classification, tool routing — and leaves the hard reasoning to the commercial plan. The effect is to roughly double usable throughput without increasing monthly spend.

The same machine also hosts websites and development environments. These workloads use different resources than language models do — network and disk rather than memory bandwidth — so they coexist without meaningfully slowing each other. One machine, two jobs, no additional hardware.

Risks, plainly

  • The local machine will not match the commercial service on hard problems. The best freely available model that fits this hardware scores around 60% on a standard software-engineering benchmark. Useful, not equivalent. The plan assumes a split workload, not a replacement.
  • Every PW-1x figure is still an estimate. The upper bound is arithmetic; the published range is a judgement call discounted below it. Nothing has been benchmarked on PW-1x, which does not exist yet, so these could move ±30% in either direction. The one real measurement so far is gpt-oss-20b on the desktop, and it came in below what this document predicted — which is the argument for replacing the rest with measurements rather than trusting them.
  • Component prices are volatile. Both memory and flash storage are in supply squeezes. Quoted prices have moved within days during this build.
  • One assumption is untested: that a large local model is genuinely more useful here than a small fast one. A free test on existing hardware settles it before further spend.

Model set

Constrained to US-origin open-weight models. Throughput figures are estimates rather than benchmarks, except the one marked † — measured on the desktop, Sept 2026.

How the estimates were derived, and why they are below the naive number. Raw weight-streaming math — 140 GB/s divided by active-parameter bytes — gives a ceiling of roughly 51 tok/s for gpt-oss-120b and 14 for Scout. Those assume nothing but expert weights crosses the bus. Real decode also pays for attention compute, KV cache traffic, MoE routing, and the GPU/CPU boundary. The figures below discount for that — more heavily for gpt-oss-120b, whose 5.1B active set is small enough that fixed overheads weigh proportionally more. The discount is judgement rather than measurement. Treat the range as a guess bracketed by a hard ceiling, and replace it with real numbers once the machine runs.

--n-cpu-moe N pushes the top N expert layers to CPU, counting down from the highest-numbered layer, overriding the -ngl 999 that placed everything on the GPU. Start high and tune down until VRAM is nearly full. Batch size -b 4096 -ub 4096 is the difference between usable and painful prompt processing — it is the setting most often left at defaults.

Serves an OpenAI-compatible API at /v1. Any agent harness that accepts a custom base URL can point at it.

Second role: web and development hosting

Websites and dev environments are close to the ideal secondary workload here. They are network- and disk-bound, idle most of the time, and do not stream data from memory the way model inference does.

Two things to get right

Co-location is the real risk, not performance. A public website sharing a host with development environments and the model stack means a compromised site sits next to everything else. Containers help but are not a hard security boundary. Anything internet-facing runs in rootless Podman, and the host is treated as exposed.

Builds are the one workload that fights inference. A large parallel compile grabs every core and does hit memory hard — that is when token latency spikes. Cap build parallelism (-j16, not -j32) rather than letting a build take the whole machine.

Isolation

Use systemd resource control rather than hoping the scheduler sorts it out. A runaway container must not be able to starve inference, and a long prefill must not stall the web stack.

# verify enumeration FIRST — sibling order varies by kernel and BIOS
#   lscpu -e=CPU,CORE   → shows which logical CPUs share a physical core

# /etc/systemd/system/llama-server.service.d/limits.conf
[Service]
AllowedCPUs=0-11,32-43   # 12 physical cores + their SMT siblings
MemoryMax=76G
CPUWeight=100

Two ways to get this wrong

The CPU is 32 cores / 64 threads. Linux enumerates 0–63, not 0–31. Pinning inference to 0-11 alone leaves logical CPUs 32–43 — the SMT siblings of those same physical cores — free for containers to land on, so the isolation does nothing. Pin core and sibling together, and confirm the pairing with lscpu -e before trusting the ranges above.

Do not over-commit memory. 128GB total: 76GB cap for inference, 40GB for containers, ~12GB left for the host and page cache. Caps that sum above 128GB mean the OOM killer decides which workload dies, and it will usually pick the 63GB process.

Containers get their own limits and stay off those CPUs. If NPS2 or NPS4 is ever enabled in BIOS, inference can be bound to specific NUMA domains — isolating memory bandwidth as well as cores. Only worth doing if contention is actually observed; start at NPS1.

Stack

  • Debian or Ubuntu Server, bare metal. No hypervisor — GPU passthrough to a guest adds real complexity and buys nothing here.
  • Podman for containers. Rootless by default, no daemon, Docker-compatible CLI.
  • Caddy as reverse proxy. Automatic Let's Encrypt certificates in roughly three lines of config.
  • Tailscale (free tier) for reaching dev environments remotely without opening ports.
  • llama.cpp as a systemd unit with the CPU pinning above.

All four are free and open source. No licensing cost in this stack.

Storage

The 1TB NVMe was sized for the OS plus two or three models. Container images and dev repositories make it tighter than that — image sprawl accumulates fast. Put /var/lib/containers on its own partition so a runaway pull cannot fill the disk out from under the model files. The second M.2 slot is free if more capacity is needed later.

Constraints and gotchas

Read these before assembly

  • No SATA ports on this board. Storage is 2× M.2 plus OCuLink and miniSAS HD. Any SATA device needs a breakout cable. This is why the archive drive stays in its USB enclosure.
  • The first M.2 socket can be switched off by a jumper. Read off the board’s Quick Installation Guide, 14 Sept 2026: M2_1 shares lanes with the PCIE2 slot, the second miniSAS connector and both OCuLink ports, and the PE16_SEL jumper decides which are live. In two of the four documented positions M2_1 is dead — a drive in it simply does not appear, with no error. M2_2 is not in that table and no jumper affects it. Put the system SSD in M2_2.
  • There is no power button on this board, and no processor fan header. The complete component list has neither: the only buttons are the rear UID1 identification switch and NMI_BTN1, and all seven fan headers, FAN1–FAN7, are system fan connectors. Power comes from the IPMI page or from shorting two pins on PANEL1; the cooler goes on FAN1. A Dr. Debug two-digit display, not beep codes, is what names a failed POST.
  • Never mix RDIMM and LRDIMM. The installed memory is RDIMM. Any future capacity change replaces all eight modules, it does not add to them.
  • Server board on an open bench has no directed airflow over the passive VRM heatsinks or the DIMM bank. Read the IPMI sensors under sustained load before deciding whether a fan is needed.
  • Build CPU-only for now; check the log when that changes. PW-1x has no card, so a CPU-only build is the correct one. When a GPU is fitted, rebuild with CUDA and confirm device detection in the startup log — a CPU-only build on a machine that has a card loads fine and runs at a crawl, which reads as "slow model" rather than "wrong build".
  • ~140 GB/s is a hard ceiling, inherent to the SP3 platform. Genoa's ~460 GB/s requires a different socket, board and memory generation.
  • PW-1x has no GPU, and the desktop’s is 8GB. gpt-oss-20b needs 12.1GB of weights, so it does not fit that card at all: measured, it runs at 39 tok/s with roughly half its layers on the processor. Any card bought for PW-1x wants 24GB or more to hold the small model and the large one’s attention layers at the same time.
  • Zen 2 is excluded from AMD's ZenDNN, which gives 2–4.5× faster prompt processing on Milan and newer. Not academic: PW-1x runs CPU-only, so nothing offloads prompt processing and this is a live cost.
  • Single socket, permanently. One CPU, no second.
  • Uptime is coupled. Anything hosted here goes down when the box reboots for a kernel update, and every experiment with the inference stack is a risk to those services. Reloading a model after a restart is cheap — about twelve seconds off the NVMe — but a host reboot takes everything with it.

Upgrade path, in priority order

  1. A GPU — PW-1x has none. Six x16 slots free. Directly attacks prefill and context headroom, and is what allows the small and large models to run concurrently. Measure CPU-only prefill first; that number is what the purchase is judged against. A used RTX 3090 24GB runs ~$1,050 as of Sept 2026; a used AMD Instinct MI50 32GB at $250–380 (Sept 2026) is the budget route, paid for in community-maintained drivers rather than dollars. Nothing existing is replaced.
  2. CPU swap — price the cheap one first. Staying on Rome, a used EPYC 7532 ($140–243 as of Sept 2026) is the same 32 cores with 256MB L3, meaning eight chiplets against the 7452’s four and twice the fabric between cores and memory. Whether that converts into real bandwidth is a measurement rather than a certainty — the 7452 has tested in the same STREAM band as 8-chiplet parts — so run the bandwidth check on arrival and buy only if the number disappoints. Milan is the expensive version: a 7543P (~$950) adds ZenDNN and Zen 3 IPC at eight times the price of the current chip, for a fraction of a GPU’s benefit. Milan is still AVX2; AVX-512 is not reachable on this socket.
  3. Memory to 512GB. Eight 64GB modules. Verify 64GB dual-rank at 3200 against the board QVL first — not confirmed. Only worth it for 400B-class models this bandwidth barely supports.
  4. OCuLink storage expansion. Two Gen4 x4 ports for external NVMe or a drive cage.

  3. Then memtest86+, all eight modules, full passes, overnight. Inside the 30-day return window, counted from delivery — no later than 13 October 2026, and earlier if the invoice shows the kit landed before 13 September.   4. Load under sustained inference and read IPMI VRM and DIMM temperatures. Add a ~$12 fan aimed at the DIMM bank only if the numbers call for it.
  5. Build llama.cpp CPU-only, load gpt-oss-120b Q8_0 fully in RAM. Record actual tokens/sec, decode and prefill on a 32k context, and replace the estimates in this document. Prefill is the number that decides whether a GPU is worth buying.
  6. Close the three open memory quote threads (Topmemory, memory.net, TechMikeNY) with a one-line note. Keep the contacts — future GPU and CPU purchases come from the same channel.
